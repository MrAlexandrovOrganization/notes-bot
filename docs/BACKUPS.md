# Внешние резервные копии notes-bot

Канонический код — `scripts/notes_backup.py`, systemd units — `ops/backup/`.
Первичная административная установка выполняется отдельно от CD: копия скрипта
в `~/.local/lib/notes-backup/` на источнике и ASUS, units в `/etc/systemd/system/`
на ASUS. Изменения скрипта требуют явного обновления установленных копий.

## Состав и гарантии

Архив содержит весь `/home/maxim/Yandex.Disk/notes`: вложения, скрытые файлы,
`.obsidian`, `.git`, незакоммиченные и игнорируемые файлы. Исходный Git не меняется:
нет автоматических commit/add/reset/push. Ссылки сохраняются как ссылки.
До и после архивации проверяются список и SHA-256 каждого файла, затем содержимое
самого архива. Если данные меняются, выполняются до трёх попыток; смешанный снимок
не публикуется. При непрерывных записях backup завершится ошибкой для повтора.

Также сохраняются `pg_dump -Fc` обеих БД (напоминания/голосовые задания и поиск),
приватная `.env`, весь `~/.config/yandex-disk` с токеном, manifest с SHA-256,
ревизией приложения и immutable digests образов БД. Приложения не останавливаются;
каждый дамп PostgreSQL консистентен, но единой транзакции между файлами и двумя
БД нет. Для переноса нужен отдельный финальный снимок при остановленных writers.

Это backup локального vault, а не всех данных облачного Яндекс Диска.
Остальные облачные папки и transient `.sync` не входят в почасовой архив.
При переносе клиента отдельно сохраняются **весь** локальный `Yandex.Disk`,
включая `.sync`, и конфигурация при остановленном клиенте. Нельзя запускать
старую копию синхронизации после появления новых записей на новом хосте.

Общие Kafka, Redis и location в архив не входят. Напоминания и durable voice
хранятся в PostgreSQL; очередь Kafka и Redis UI-state требуют отдельного
переноса/согласования при восстановлении. Отправка Telegram не откатывается
вместе с БД: перед включением consumers проверять очередь и возможные повторы.

## Расписание и доступ

ASUS забирает архив каждый час в `:20` по Москве с задержкой до 120 секунд.
Timers persistent, при ошибке backup до трёх попыток за час с интервалом 5 минут.
Хранение: все архивы 48 часов, затем последние за 7 UTC-дней, 4 ISO-недели
и 12 месяцев с доступными копиями. Ротация выполняется только после успешной
передачи и проверки нового архива. Незавершённые копии не заменяют рабочие.

На ASUS каталог `~/backups/notes-bot` имеет 0700, архивы 0600.
SSH шифрует передачу, архивы на диске не зашифрованы: содержат личные данные
и секреты. Их не добавляют в Git, CI artifacts или логи.
`latest.json` содержит дату, размер, SHA-256 и fingerprint vault.

Отдельный ключ создаётся и остаётся только на ASUS в `~/.config/notes-backup/`.
`config.json`: `directory`, `source=maxim@<tailnet-IP>`, `identity`, `known_hosts`.
На источнике разрешается только forced command:
`/usr/bin/python3 /home/maxim/.local/lib/notes-backup/notes_backup.py source`
с `restrict,from="100.64.0.11"`. Host key получают по уже доверенному каналу
администратора; строго проверяют через отдельный known_hosts. Существующие
authorized_keys, cron и другие backup units не заменяются.

## Проверка восстановления

Первого числа месяца в 05:10 МСК ASUS распаковывает vault в изолированный
временный каталог, сравнивает все файлы и выполняет `git fsck --full`.
Обе БД восстанавливаются **по очереди** в отдельные PostgreSQL-контейнеры
из digest исходного образа: без сети, портов и production mounts, RAM 512 MiB,
1 CPU. Данные БД на отдельном временном Docker volume, удаляемом вместе
с контейнером. Выполняются `pg_restore --exit-on-error --single-transaction`,
проверка чтения всех таблиц. Production credentials и приложения не запускаются.
Результат — `verified.json`. Для образов требуется доступ к registry/cache.

```sh
sudo systemctl start notes-backup.service
sudo systemctl start notes-backup-verify.service
systemctl list-timers 'notes-backup*' --all
systemctl show notes-backup.service notes-backup-verify.service -p Result -p ExecMainStatus
cat ~/backups/notes-bot/latest.json ~/backups/notes-bot/verified.json
```

После аварийного kill проверить контейнеры по label `service=notes-backup-verify`;
обычное завершение удаляет fixture и его анонимный volume. Об ошибках пишет
journal; отдельные внешние уведомления о просроченном backup пока не настроены.
На offline ASUS новых копий не будет; следить за свежестью `latest.json`.
Для остановки расписания сохранить архивы и отключить только `notes-backup*` timers.

Prerequisites: Python 3.12+, Docker, OpenSSH, Git; systemd на ASUS.
`make backup-test` выполняет синтетические проверки без SSH/production и входит
в `make check`. Полное runtime-восстановление выполняется отдельно.

## Возврат данных

Выбрать архив и проверить SHA-256 всего архива и каждого вложения.
Остановить bot/web/core, scheduler, search и Yandex Disk до изменения данных.
Распаковать vault в **новый** каталог, включая `.git`, проверить fingerprint
и `git fsck`. Восстановить оба дампа в новые PostgreSQL volumes с версиями
из manifest, без удаления старых. Владельцев и пароли восстановить из приватной
конфигурации, не применять production `.env` к тестовому восстановлению.
Сначала проверить файлы, схемы и доступ приложения; затем очередь, consumers,
голосовые задания и только после этого включать Telegram и синхронизацию.
Для Yandex Disk сохранить текущий vault отдельно до первого подключения:
синхронизация и Git не заменяют резервную копию.
