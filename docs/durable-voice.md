# Постоянные голосовые задания и доставка

## Гарантии и границы

Telegram frontend сохраняет голосовое задание в PostgreSQL **до** HTTP 200
webhook или продвижения polling offset. Повтор `(chat_id, message_id)` не
меняет исходные дату/путь заметки, режим, время сообщения и UUID операции.
Недоступность Redis при первом приёме возвращает webhook 503: Telegram может
повторить доставку, а неверный snapshot не сохраняется.

Обработчик приёма создаёт статусное сообщение «Принимаю голосовое…» с кнопкой
отмены и сохраняет его ID вместе с заданием. После сохранения он сразу отправляет
отдельное сообщение с главным меню, не ожидая фонового обработчика или Whisper.
Фоновый обработчик редактирует исходный статус и показывает в нём результат.
При ошибке создания статуса или сохранения задания апдейт не подтверждается
и повторяется Telegram; при ошибке сохранения статус сообщает о повторном приёме.
На каждую отправку в Telegram отведено до 5 секунд. Ошибка отправки меню
записывается в лог и не отменяет принятое задание. Повторный апдейт не отправляет
меню заново; его доставка не сохраняется в задании и не восстанавливается
после перезапуска. Потеря ответа при создании статуса до сохранения задания
может оставить дополнительное статусное сообщение.

Статус показывает этапы скачивания и отправки аудио, ожидание воркера и
процент расшифровки, когда backend передаёт положительную оценку прогресса.
Оценка приблизительная; без неё отображается «Расшифровываю…».
Повторяющиеся значения не редактируют сообщение заново, в том числе после
перезапуска. Кнопка отмены сохраняется при каждом обновлении прогресса.
Ошибка Telegram при обновлении прогресса не останавливает обработку задания.

Фоновый обработчик восстанавливает из БД загрузку, backend job ID, результат,
подтверждение получения и доставку. Общего срока ожидания нет; недоступность
Whisper, core, LLM или Telegram приводит к повтору с задержкой. Каждый шаг
ограничен 180 секундами, lease — 240 секундами; следующий процесс забирает
незавершённую работу после истечения lease. UUID lease и проверка срока не
дают старому процессу переписать состояние нового владельца.

Backend получает стабильный `request_id=notes-bot:<UUID>` и
`retain_until_ack=true`. Повтор загрузки после потерянного ответа не создаёт
вторую транскрибацию. Текст/ошибка сначала записываются в frontend PostgreSQL,
и только следующим шагом отправляется `Ack`. После этого срок хранения
backend результата не влияет на доставку. `Ack: NOT_FOUND` при уже сохранённом
локально результате безопасен: предыдущий Ack мог выполниться до потери ответа
и последующего удаления backend записи.

Результаты доставляются по исходному MessageID внутри чата. Обычная запись в
дневник использует `AppendToNote(operation_id=voice:<UUID>)`. После «Дописать»
путь открытого файла сохраняется в `active_relpath` JSON payload задания;
доставка использует `AppendToNoteByPath(operation_id=voice:<UUID>)` с этим
путём, даже после перехода к другой заметке, повтора апдейта или перезапуска.
Ключ повтора для записи по пути действует в пределах выбранного файла;
задание не меняет свой путь на повторе. Если файл удалён/недоступен, запись
повторяется без перенаправления в дневник и без создания новой заметки.
Путь также показывается в сообщении о сохранении. Текст и скрытый
HTML marker записываются атомарно с fsync. Повтор после потерянного gRPC ответа
не добавляет текст второй раз. Нельзя удалять marker, пока возможны повторы;
ручное удаление заметки/marker убирает эту гарантию. Межпроцессные flock защищают
writers core на общем локальном файловом хранилище; это не схема распределённого
хранилища заметок между VPS и не координация с внешними редакторами.

Финальная Telegram доставка редактирует сохранённое сообщение, повторяясь
без дублирования текста. Если сообщение удалено, создаётся новая точка доставки.
Telegram SendMessage не имеет idempotency key: потеря ответа при первоначальном
создании/восстановлении сообщения может оставить дополнительное статусное
сообщение. Запись в заметку при этом остаётся идемпотентной. Постраничное чтение
использует сохранённый текст и UUID задания, переживает restart и замену сообщения.

Для smart/NL режима сохраняются время исходного сообщения и подготовленный
результат LLM. «Сегодня»/«завтра» вычисляются относительно этого времени и
сохранённой TZ/границы дня. Результат появляется с кнопкой открытия: позднее
распознавание не перезаписывает текущую сессию пользователя автоматически.
Открытие восстанавливает конкретный draft, подтверждение привязано к UUID
голосового задания. Ручное создание задач/напоминаний использует существующие
подтверждения; гарантии всего notifications API не расширяются этим изменением.

Завершённые frontend задания и текст пока не удаляются автоматически.
Нужны резервные копии notes-bot PostgreSQL и каталога заметок. Отказ самой БД,
утрата диска или недоступность Telegram файла до загрузки не устраняются журналом
доставки. Для HA этих данных необходим отдельный этап репликации и восстановления.

## Миграция и доставка

Добавление `active_relpath` не меняет SQL-схему: поле хранится в существующем
JSONB payload. Старые задания без этого поля продолжают запись в исходный
дневник; исторический путь восстановить из них нельзя. Перед включением нового
Telegram frontend обновить core: прежний core игнорирует новый `operation_id`
в `AppendToNoteByPath` и не обеспечивает идемпотентность этого RPC. Штатный CD
обновляет оба образа; Telegram зависит от healthcheck core.

1. Обновить **весь** `backends/transcriber`, включая постоянный worker.
   Старый worker содержит прежний TTL cleanup и несовместим с новым retention.
2. Обновить notes-bot обычным Git/CI/CD. `make up` вызывает явный
   `make migrate-voice`: поднимает существующий postgres, собирает telegram,
   запускает `/telegram migrate-voice`, затем обновляет сервисы.
3. Обычный startup Telegram только проверяет схему. Миграция выполняется
   транзакционно с advisory lock и ledger `voice_schema_migrations`; добавляются
   отдельные таблицы, существующие reminders не изменяются.
4. Удалённые inference workers подключаются к отдельному WorkerService через
   gRPC/TLS с индивидуальными credentials. Worker не получает Telegram token,
   notes DB credentials или доступ к заметкам.

Незавершённые задания прежней RAM реализации не могут быть восстановлены
задним числом. До rollout следует дождаться их завершения. Для отката приложения
оставлять добавленные таблицы и колонки; не выполнять разрушительный downgrade.

Snapshot `proto/whisper/whisper.proto` синхронизирован из канонического
`MrAlexandrovOrganization/transcriber`, ревизия `d583af6`.
Обычные сборки не обращаются к соседнему checkout; обновление snapshot — явная
операция `make proto`. Generated Go stubs создаются через `make proto-generate`.

## Наблюдаемость и проверки

На существующем Telegram `/metrics` публикуются:

- `telegram_voice_jobs_pending`, `telegram_voice_jobs_ready_undelivered`;
- `telegram_voice_jobs_cancelled_pending`, `telegram_voice_jobs_oldest_pending_age_seconds`;
- `telegram_voice_database_available`, `telegram_voice_database_last_success_seconds`.

Фактическое имя Prometheus зависит от OTel normalization; проверяется после
деплоя. При ошибке БД availability=0, число заданий не подменяется ложным нулём.
Логи повторов содержат UUID операции без аудио, текста, file ID и секретов.
OTel контекст сохраняется в задании и восстанавливается для каждого шага.

```bash
make check PROTO_BREAKING_AGAINST='.git#ref=HEAD,subdir=proto'
make lint-golangci
make test-voice-db-up
TEST_VOICE_DATABASE_URL='postgres://voicejobs_test:synthetic-voicejobs-test@127.0.0.1:55442/voicejobs_test?sslmode=disable' make test-voice-db
make test-voice-db-down
```

`make check` генерирует ignored stubs/views, проверяет protobuf совместимость,
gofmt/vet, unit/race и существующие integration tests. PG tests используют только
явно заданный loopback DB URL, случайную схему на каждый тест и синтетические
данные. Проверяются повтор миграции, restart, конкурентные claims, expiry/fencing,
cancel, порядок доставки и метрики. Handler tests моделируют потерянные ответы,
долгую недоступность, сохранение результата до Ack, повтор append и pagination.
Обычные tests не отправляют Telegram сообщения и не меняют production.

## Transcriber на другой машине

Telegram frontend обращается к общему backend по gRPC. Docker Compose читает
`WHISPER_GRPC_HOST` и `WHISPER_GRPC_PORT` из `.env`; значения по умолчанию —
`whisper-ingress:50053`. Это может быть как сам backend, так и локальный прокси.
Для backend на другой машине задайте его адрес в доверенной VPN-сети и порт
клиентского API, затем примените настройки обычным Git/CI/CD деплоем.

Публичный TLS WorkerService предназначен для inference workers и не заменяет
клиентский API Submit/GetStatus/Ack. Внутренний клиентский gRPC работает без
отдельного TLS, поэтому удалённое соединение должно проходить через защищённую
VPN-сеть. Compose включает выбранный host в `NO_PROXY`, чтобы прокси Telegram
не перехватывал этот трафик.

Docker-сеть `whisper-net` сохраняется для совместимости с локальным сервисом
или forwarder; при прямом VPN-соединении frontend не зависит от процессов
Transcriber на своей машине. Задания, UUID повторов и результаты продолжают
храниться в PostgreSQL notes-bot. Временная недоступность удалённого backend
вызывает повтор обработки по описанной выше политике.
