# Автоматизации Notes

Первая версия связывает **изменение статуса выбранной задачи → уведомление
в Telegram**, сразу либо с задержкой до 30 дней. Выполнение учитывается через
существующие Core RPC из Telegram, Web и Android Notes. Ручные правки Markdown
и синхронизация Obsidian не создают события в этой версии.

## Настройка

В Telegram: «⚡ Автоматизации» → «После изменения задачи» → выбрать задачу
активного дня → выбрать статус → текст → задержка в минутах → один раз/каждый
такой переход → подтвердить. Для другого дня сначала выберите дату в календаре.
В Web есть раздел `/automations` с выбором даты, задачи и параметров уведомления.
Android продолжает использовать прежний endpoint смены статуса; обновление APK
для срабатывания уже настроенных правил не требуется. Настройка правил в этой
версии доступна в Telegram/Web, доставка уведомлений — в Telegram.

Пример: задача «Отправить отчёт» → выполнена → через 30 минут «Проверить ответ».
Текущее завершённое состояние при создании правила не считается новым событием.
Повторное сохранение того же статуса не создаёт событие. Возврат задачи в работу
и новое выполнение создают новый переход; повторяемое правило сработает снова.

Задержка отсчитывается от события. Возврат задачи к другому статусу не отменяет
уже запланированное уведомление. Удаление правила отменяет ожидающие действия;
уже начавшаяся отправка может успеть завершиться. После наступления срока у
доставки есть 24 часа на повторы — пяти-минутный TTL геонапоминаний здесь не
используется. Одноразовое правило расходуется при создании задания, а не при
прочтении уведомления. История показывает pending/sending/sent/expired/cancelled
человеческими подписями, дату и число попыток.

## Идентичность и сохранность

Привязка — к дате и постоянному UUID задачи, а не номеру строки. UUID назначается
при явной привязке либо первом изменении через включённый Core. Старые заметки
массово не переписываются. В строке сохраняется служебный HTML-комментарий с ID,
ревизией и ID последнего события. Комментарий скрывается в пользовательском
Core API, списках задач и поисковой материализации; исходный Markdown сохраняет
метаданные. Перестановка строк внутри дня не меняет привязку. Перенос в другой
файл/день требует нового правила. Дубликаты ID в одном файле отклоняются.

Core сохраняет намерение в `Daily/.<date>.md.task-intent.json` перед атомарной
записью заметки. Запись задачи, её статуса и event stamp происходит одним
fsync+rename под существующей межпроцессной блокировкой файла. Затем событие
публикуется в `.notes-bot-task-events/` внутри того же persistent vault. Локальный
`.gitignore` в этой служебной папке исключает очередь из Git. Для vault Git
также исключите `Daily/.*.md.task-intent.json`; это журнал, его не следует
публиковать в истории. При резервном копировании vault оба вида файлов сохраняйте.

При сбое до записи заметки намерение отменяется. После записи факт подтверждается
хэшем файла либо event stamp задачи; Core восстанавливает событие. Неоднозначная
конфликтующая правка не превращается в выдуманное выполнение: очередь остаётся
для диагностики, Poll повторяется и увеличивает метрику ошибки. Нельзя удалять
intent/outbox вручную, пока не выяснено состояние операции. Ручные правки
Obsidian не участвуют в блокировке Core и остаются вне гарантий этой версии.

Notifications читает CoreEventsService каждые пять секунд. В одной PostgreSQL
транзакции сохраняет неизменяемое событие в inbox, создаёт исполнения подходящих
правил и обновляет состояние once. Затем подтверждает событие Core. Потерянный
ACK даёт повтор, но не второй эффект: проверяются source+event ID, хэш payload и
уникальность исполнения. Очередь Core предназначена для одного логического
потребителя — моста Automations; несколько правил обрабатываются внутри него.
Не подключайте второй независимый consumer, удаляющий тот же outbox.

Telegram забирает действия с lease 45 секунд; HTTP-send ограничен 20 секундами,
ACK — пятью. Геонапоминания и автоматизации используют общий обработчик сроков
и подтверждений. Существующие геотаблицы/API/правила не мигрируются и продолжают
работать самостоятельно. Повторы Telegram send после потери ответа могут дать
дубликат сообщения: exactly-once для внешнего Telegram API не обещается.

## Расширение

`proto/automation/v1/automation.proto` задаёт общий envelope ID/source/type/subject/
время/trace context и типизированный payload. Первый зарегистрированный тип —
`notes.task.status_changed.v1`; первые trigger/action — TaskStatus и Notify.
Новые источники добавляют типизированный payload, валидацию и адаптер доставки
с подтверждением; новые действия — обработчик, идемпотентность эффекта и UI.
Прямой публичный publish/webhook, произвольный код и новые брокеры не добавлены.
Перед действиями, которые сами изменяют данные, понадобятся causation context
и ограничение циклов. Создание задач, изменение полей и перенос геоправил в общий
движок — следующие расширения, они пока не включены.

## Включение и откат

Флаг `AUTOMATIONS_ENABLED=false` по умолчанию. Перед включением сохранить внешний
backup PostgreSQL и vault, включая Git, скрытую очередь и незавершённые intents.
Проверить доступ UID Core к vault и `.notes-bot-task-events`: startup проверяет
возможность записи до приёма запросов.

1. Доставить согласованные Core, Notifications, Telegram и Web через Git/CI.
2. Явно выполнить `make migrate-automations` до включения. Digest activation и
   `make up` уже вызывают миграцию до старта приложения. История — отдельная
   `automation_migrations`, advisory lock и транзакция. Старые таблицы не меняются.
3. Установить `AUTOMATIONS_ENABLED=true` в приватной конфигурации всех ролей и
   активировать опубликованные digest штатным способом. Core и Notifications
   должны включаться вместе. При отдельном mobile gateway обновить его до
   соответствующего опубликованного Web digest; сам APK остаётся совместимым.
4. Создать синтетическую задачу и правило, выполнить через каждый нужный клиент,
   проверить историю, отправку, задержку, повтор статуса и перезапуск.

Для отключения убрать флаг у всех ролей. Данные и очередь сохранить: при
повторном включении bridge обработает сохранённые события с учётом дат правил
и сроков заданий. Откат старого Core после назначения ID требует сохранить
совместимость с метаданными строк: старые парсеры могут показывать комментарии.
Полный возврат старых vault/БД поверх новых записей не является безопасным откатом.
Восстанавливать vault и inbox нужно согласованно; конфликт source/subject/revision
не исправлять обнулением таблиц или регенерацией ID.

Метрики: `core.automation.events.pending`, `notifications.automation.executions`
с ограниченным label status, `notifications.automation.oldest.pending.age`,
`notifications.automation.poll.failures`. Новые логи не содержат текста задач,
уведомлений или event payload. Наличие endpoint само по себе не подтверждает
сквозной сбор в Grafana.

## Проверки

`make check` включает контракты, Go/race, vet, UI и самодостаточные интеграционные
тесты. `make test-automations-db` использует отдельную случайную схему только
в loopback БД `voicejobs_test` либо `automations_test`; не передавайте рабочий DSN.
CI использует существующий изолированный PostgreSQL fixture и те же Make-цели.

Покрыты восстановление до/после записи файла, конкурентные смены статуса,
постоянство ID после перестановки, устаревший выбор задачи, gRPC Core → inbox →
задание с потерянным ACK, дедупликация, delay/once/repeat, lease, отмена, права,
экранирование Web/Telegram и сохранение черновика. Обычные тесты не подключаются
к рабочему vault/БД и не отправляют настоящие сообщения.
