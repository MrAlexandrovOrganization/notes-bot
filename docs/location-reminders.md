# Напоминания по месту

Первая версия: именованные круглые места, подтверждённые вход/выход и уведомления
в Telegram. Повторение: следующий переход один раз, каждый переход или максимум
раз в календарный день выбранного часового пояса (по умолчанию Europe/Moscow).
Автоматическое создание задач, ограничения по будням/часам, Web/Android Notes UI
и локальный детектор на телефоне в эту версию не входят.

## Использование

В главном меню Telegram нажмите «📍 Места и события» → «Добавить место».
Введите название, отправьте обычную геопозицию на карте либо `широта долгота`,
задайте радиус 100–10000 м и подтвердите. Выбранная точка задаёт геометрию места:
бот не записывает её как фактическое перемещение телефона.

В карточке места выберите «Когда приду» / «Когда уйду», введите текст, выберите
повторение и подтвердите. Создание привязано к следующему переходу: пребывание
внутри в момент создания правила не вызывает уведомление. «Напоминания по месту»
позволяют удалить правило; удаление места отключает связанные правила.
Одноразовое правило остаётся в списке с отметкой после срабатывания.

Используйте немедленную отправку координат в Locations. В режиме «раз в час или
100 точек» данные приходят поздно и намеренно не запускают актуальные уведомления.
GPS на телефоне и сеть могут задержать или пропустить переход; это не система
контроля доступа. Первые подтверждённые измерения после включения, изменения зоны
или разрыва данных более пяти минут задают исходное состояние без события.

## Границы и доставка

Location владеет местами, состояниями и последовательным журналом переходов.
Канонический контракт — `backends/location/proto/location/v1/location.proto`.
Notifications читает журнал через авторизованный приватный gRPC каждые 10 секунд.
Курсор и задания доставки фиксируются одной транзакцией в существующей БД Notes.
Триггер Location атомарно сохраняет намерение обработки вместе с точкой;
состояние, событие и удаление этого намерения также фиксируются вместе.

Выбран durable pull через gRPC, чтобы не добавлять Location зависимость от Kafka.
У существующих уведомлений по времени сохраняется их прежний путь Kafka.
Новые уведомления используют PostgreSQL очередь с lease 45 секунд, уникальностью
`rule_id,event_sequence`, повторными попытками до истечения срока и статусами
`pending/sending/sent/expired/cancelled`. Telegram забирает задания каждые 5 секунд.
Это отдельная доставка событий, не расписание с искусственным `next_fire_at`.

Срок актуальности по умолчанию — пять минут с подтверждения перехода; API принимает
60–3600 секунд. Просроченное событие не расходует одноразовое правило. Если уже
созданное задание истекло до отправки, оно получает `expired`, а одноразовое правило
считается сработавшим. После сетевой ошибки доставка повторяется с ограниченным
backoff. У Telegram нет идемпотентного send: обрыв после отправки и до подтверждения
может дать повторное сообщение. Нельзя обещать exactly-once.

Настройка места/создание правила используют сохранённый в черновике UUID запроса:
повтор после потери ответа не создаёт второе место или правило.

Метрики: `location.geo.evaluations.pending` и `notifications.geo.deliveries`
с ограниченным label `status`. Координаты, названия мест и токены новые обработчики
не пишут в логи/labels. Журнал и очередь нужно включать в существующие резервные
копии БД. Журнал не очищается автоматически: нельзя удалять события перед курсором
без согласования с потребителем. Восстановление Location и Notes из разных точек
времени требует сверки журнала/курсора; не обнуляйте курсор для рабочего пользователя
без проверки TTL и истории исполнений.

## Включение и доставка

Функция выключена, пока адрес и токен не настроены. Обычный запуск Notes не применяет
новую схему. `make migrate-geo` — явная миграция; `make up` и digest activation
вызывают её до запуска приложения. Миграции транзакционные, под advisory lock,
с отдельной историей `geo_migrations`. Старые таблицы напоминаний не изменяются.

1. Сохранить внешние бэкапы обеих БД и проверить доступ к восстановлению.
2. В Location создать отдельный случайный секрет через `make geo-device`.
   Внести `GEO_TOKEN_SHA256` из приватного файла в конфигурацию Location.
   Мобильный bearer для управления местами не использовать.
3. Доставить Location через его Git/CI: активация явно применяет миграцию 011.
   gRPC слушает 50056, опубликован только на loopback:15056. Для разных хостов
   отдельно предоставить этот endpoint через существующий защищённый tailnet
   механизм; не открывать его в публичный интернет. Старый HTTP порт 18084 не подходит.
4. В приватной конфигурации Notes указать `GEO_LOCATION_ADDR=host:port`,
   `GEO_LOCATION_TOKEN` и существующий положительный `ROOT_ID`. На одном Docker-хосте
   можно использовать `location:50056`: notifications подключён к location-api-net.
   Russia overlay использует приватный межхостовый endpoint, не Docker DNS Finland.
5. Доставить Notes через Git/CI: активация вызывает `/notifications migrate-geo`
   из того же опубликованного digest перед запуском.
6. Включить немедленную доставку в Locations и проверить одно место на реальном
   маршруте: начальное состояние, выход, возврат, пропадание сети, перезапуск.

После доставки нужно отдельно подтвердить приватное gRPC-соединение, доставку
Telegram и реальные переходы телефона. Конфигурация относится к одному
основному Android-трекеру одного владельца. Несколько установок с общим mobile
bearer смешивают позиции: для нескольких телефонов сначала нужен отдельный
аутентифицированный device identity и выбор основного устройства.

Для отключения убрать обе переменные GEO_LOCATION_* и GEO_TOKEN_SHA256, затем
доставить конфигурацию штатным способом. Данные оставить. Старые бинарники работают
с добавленными таблицами; откат не должен удалять SQL-историю или новые данные.

## Контракт и проверки

Snapshot Location лежит в `proto/location/v1/location.proto`; snapshot.json фиксирует
источник и SHA-256. Snapshot закреплён за коммитом канонического репозитория Location.
Для следующего обновления укажите окончательную ревизию источника:

```sh
make proto-location-sync LOCATION_PROTO_SRC=/path/to/location/proto/location/v1/location.proto LOCATION_SOURCE_REVISION=<commit>
make proto-generate
```

Обычный build/check не читает соседний checkout и не обновляет snapshot из сети.
Канонический go_package сохраняется; M mapping передаётся обоим Go-плагинам.
`make check` проверяет hash, Buf lint/build/breaking против выбранной предыдущей
ревизии, Go tests/race, vet, UI и конфигурацию. Новые stubs игнорируются и генерируются
до сборки и внутри Docker. Проверка hash подтверждает неизменность snapshot,
а не равенство текущему соседнему репозиторию.

```sh
make check PROTO_BREAKING_AGAINST='.git#ref=<previous-commit>,subdir=proto'
make test-voice-db-up
TEST_GEO_DATABASE_URL=postgres://voicejobs_test:synthetic-voicejobs-test@127.0.0.1:55442/voicejobs_test?sslmode=disable make test-geo-db
make test-voice-db-down
```

DB-тесты создают отдельную случайную схему только в loopback БД `voicejobs_test`
или `georeminders_test` и удаляют именно её. CI использует ту же цель. Обычные тесты
не обращаются к рабочим БД/Location/Telegram. Они покрывают конкурирующих потребителей,
повторную доставку, перезапуск lease, сроки, once/daily/always, старые события,
права владельца, сохранение UI-черновика и экранирование пользовательских строк.
