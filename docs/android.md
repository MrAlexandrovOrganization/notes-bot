# Notes для Android

Нативный клиент — отдельный репозиторий `android/notes-app`. Использует тот же
vault, Core, Search, Notifications и `ROOT_ID`. Обычный публичный сайт не
регистрирует `/mobile/v1/*`: отдельный экземпляр проверенного `/web` запускается
с `WEB_MOBILE_ONLY=true` и публикуется только на tailnet IP.

## Контракт

HTTP/JSON выбран для мобильной границы: стандартный Android HTTP/TLS без
дополнительного gRPC ingress; внутренние вызовы остаются gRPC. Вход
`POST /mobile/v1/session {"password":"..."}` использует пароль сайта и его
rate limiter. Возвращает `token`, передаваемый как `Authorization: Bearer ...`.
Фиксированный срок сессии — 30 дней. `DELETE /mobile/v1/session` отзывает её
до перезапуска экземпляра (список отзыва, как у сайта, хранится в памяти).
APK хранит только сессию под Android Keystore, пароль не сохраняет.

GET: `bootstrap` (сегодня, даты, UTC offset и начало логического дня),
`day?date=DD-Mmm-YYYY`, `directory?path=...`, `note?path=...`, `search?q=...`,
`reminders`. Снимки кэшируются на телефоне; автоматически загружаются последние
семь существующих дневных заметок, остальные — по открытию. Полная офлайн-копия
всего vault не заявляется.

`POST append` принимает `{id: UUID, date, path, text}`. Должен быть задан ровно
один из `date`/`path`. Ответ **200** с `{id: тот же UUID, stored: true}` разрешает
подтвердить операцию. Приложение дополнительно получает свежую заметку и одной
SQLite-транзакцией обновляет кэш и удаляет операцию. При любой ошибке UUID,
получатель и текст сохраняются для повтора. Core использует существующий
`operation_id=android:<UUID>` и устойчивый marker в markdown; отсутствие
идемпотентного Core приводит к 503, небезопасного fallback нет.

`POST rating {date,rating}`, `task {date,index,text,state}` выполняются только
онлайн без автоматического повтора. Индекс задачи сравнивается с её текстом,
но проверка и изменение — два gRPC-вызова: параллельное редактирование той же
заметки другим клиентом всё ещё может создать гонку. Офлайн создание задачи
идёт через idempotent append строки `- [ ] ...`.

`POST ask {question}` — серверный поиск с ответом и источниками.
`POST reminders` принимает поля `ReminderFormData` (Title, ScheduleType,
Hour, Minute, Days, DayOfMonth, Month, Day, Date, IntervalDays, CreateTask).
`POST reminders/action {id,action,minutes}` — delete/postpone. Напоминания
используют серверный ROOT_ID; клиент не выбирает user_id. Эти операции пока
не имеют durable request ID и не повторяются автоматически: после потери
ответа требуется проверить список перед повтором создания/переноса.

Размер JSON запроса ограничен 256 КиБ, неизвестные поля и несколько JSON
значений отвергаются. Ошибки не содержат текстов заметок и gRPC-ошибок.
Клиент запрещает redirect, проверяет MIME и ограничивает размер ответа.

## Уведомления

Существующая Telegram-доставка не меняется. Android сохраняет ближайший
`next_fire_at` и планирует локальный AlarmManager, умеет восстановить его
после перезапуска/перезагрузки. UUID события — reminder ID + время. Повторный
poll после показа не переустанавливает это событие. Требуются разрешение
уведомлений и, для точного времени, «Будильники и напоминания».

Это не push канал и не копия Kafka history. Изменения/отмена из Telegram
становятся известны при следующем poll; при офлайн может сработать прежнее
событие. Без сети гарантируется только ближайшее уже загруженное событие,
не все последующие повторы: серверный RPC не отдаёт параметры расписания.
Событие, которое сервер уже сдвинул до первого подключения клиента, может быть
пропущено Android. WorkManager делает периодические попытки раз в 15 минут;
Android/Doze/VPN могут увеличить задержку. Если точные alarms не разрешены,
используется inexact alarm. Force-stop требует повторного открытия приложения.

## Доставка API

Изменения подготовлены локально. Для активации сначала провести штатный CI
и публикацию `web` образа, затем взять его digest из image manifest.
Не собирать приложение на VM. На активном Russia checkout сохранить:

```env
NOTES_MOBILE_IMAGE=ghcr.io/organisation/project/web@sha256:<checked-digest>
NOTES_MOBILE_BIND_IP=100.64.0.5
```

Явная активация через корневой Makefile:

```sh
make mobile-config-check
make mobile-up
make mobile-status
```

Цели добавляют `compose/compose.mobile.yml` к текущему выбранному стеку;
`up --no-deps --no-build mobile` запускает только новый экземпляр. Не добавлять
этот overlay в обычный COMPOSE_FILE, пока image publisher не учитывает новый
сервис в manifest: он использует уже опубликованный web artifact.
Не менять `.retired`, не запускать прежний Notes на server.

Откат: `make mobile-stop`. Vault и БД не меняют схему, мобильная очередь
остаётся на телефоне. После активации проверить bind именно на 100.64.0.5,
health, отказ без bearer, успешное чтение через VPN и Android; проверка 200
health сама по себе не доказывает доступ к Core/Notifications.

Голос, серверная загрузка аудио и локальная large-v3-turbo в первой версии
не реализованы: существующий durable voice pipeline зависит от Telegram
журнала/файлов. Его перенос требует отдельного контракта загрузки и retention,
а локальная модель — NDK/JNI и замеров на realme 11 Pro. Новых ML workers
на Russia не запускается.
